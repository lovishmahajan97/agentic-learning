## TL;DR
Leakage is any path by which information that will not be available at prediction time, or that
belongs to the evaluation set, reaches the model or the metric. It makes offline numbers lie in the
optimistic direction, which is the worst direction: you ship something that collapses in production.
It rarely looks like a bug. It looks like a feature that is "surprisingly predictive", a scaler fitted
before the split, a random split of time-ordered data, or a golden set the prompt was tuned against.

## Why it exists
The whole point of a held-out set is to simulate the future: data the model has never seen, scored
once, so the number you get is an unbiased estimate of what will happen after deployment. Every
leakage mechanism breaks that simulation in a way that flatters the model. Because the error is
always in the same direction, it does not average out, and because the model is genuinely good at
exploiting the leaked signal, nothing in the training loop complains. The loss goes down, the metric
goes up, the demo works.

The naive defence, "we split the data, so we are fine", fails because splitting rows is not the same
as splitting *information*. Information crosses the split through three doors. Through the
**features**, when a column encodes the label or was recorded after the outcome (a "cancellation
reason" field on a churn dataset is populated only for churners). Through **shared entities and
time**, when the same customer, patient or document appears on both sides, or when the model trains
on April to predict March. And through the **fitting procedure**, when any statistic is computed on
the full dataset before the split: a scaler's mean, an imputer's median, a target encoder's per-category
average, the features chosen by a selection step, or, in LLM work, the prompt wording iterated against
the test set. Each door lets the test set shape the model, and the model duly scores well on it.

The reason this matters more for AI engineers than it did a decade ago is that the leaks have moved
up a level. Benchmarks sit inside pretraining corpora, golden sets get pasted into few-shot prompts,
and evaluation sets are regenerated by the model being evaluated. The mechanism is identical; only
the surface changed.

## How it works
### Target leakage: the feature is the label in disguise
A feature leaks the target when its value is caused by the outcome rather than predictive of it, or
when it is captured after the moment at which a real prediction would be made. The test is a
timestamp question: *at the instant the model would run in production, would this value exist with
this content?* Columns like "days until account closed", "number of collection calls" or a support
ticket's "resolution notes" fail that test. They are the strongest features in the model *because*
they are downstream of the label, and they vanish or change meaning at inference time.

### Row leakage: the split is on the wrong key
Random row splits assume rows are independent. They are not when one entity generates many rows
(several visits per patient, several chunks per document, several turns per conversation) or when
rows are ordered in time. A model that saw patient 17's other visits in training is partly
memorizing patient 17; a model that trained on next quarter's prices is reading the future. The fix
is to split on the unit of independence: `GroupKFold` by entity id, or a time-ordered split where
validation strictly follows training. The gap between random-split and group- or time-split scores
is itself a measurement of how much you were leaking.

Two refinements matter in practice. First, a time split needs a **gap** when labels or features span
a window. If the label is "churns within 30 days" and training ends on 31 March, the labels of late-March
training rows were decided by events in April, which is the validation period; leave at least one label
horizon between the end of training and the start of validation (scikit-learn's `TimeSeriesSplit` has a
`gap` argument; finance calls this purging and embargo). Second, entities are not always labelled for
you. Exact duplicates, near-duplicates (the same support ticket re-sent, the same paragraph in two
documents, an image and its crop) and templated rows behave like one entity in two places. Hash for
exact matches and use a near-duplicate method such as MinHash or embedding similarity across the split
boundary, *because* a random split of a corpus with 5% near-duplicates silently gives the model an
open-book exam on that 5%.

### Preprocessing leakage: fitted on everything, evaluated on part
Anything with a `fit` step learns from the rows it sees. Fit a scaler on all rows, then cross-validate,
and each fold's model trained on inputs normalized with statistics that include the fold's test rows.
For a scaler the effect is small; for feature selection or target encoding it is catastrophic, because
the selection step has already looked at the test labels to decide which columns survive. The rule
that prevents this is mechanical: every fitted transform lives inside the pipeline that is fitted
*within* each fold, on that fold's training rows only. Resampling (SMOTE, oversampling) belongs to the
same category: synthetic minority examples made from the full set put near-copies of test rows into
training.

### Selection leakage: the test set as a training signal
A single held-out set survives exactly one honest use. Every time you look at the test score and
change something (a hyperparameter, a feature, a prompt, a retrieval setting), the test set has voted
on your model and is now a weak training set. After thirty iterations the "test" number is an
optimistically biased validation number. The defence is structural: iterate on a validation split,
keep a frozen test split that is evaluated rarely and logged each time, and use nested
cross-validation when data is too small to afford three partitions.

### LLM-era variants of the same thing
- **Benchmark contamination:** public eval sets appear in web-scale pretraining data; a high score may
  be recall, not reasoning. n-gram overlap checks between eval items and training data are the
  standard, imperfect detector (see the evals module on dataset contamination).
- **Golden-set bleed:** examples from the eval set appear in the system prompt as few-shots, in the
  fine-tuning data, or in the retrieval corpus verbatim, so the system is tested on its own notes.
- **Self-generated evals:** questions written by the model under test, from the chunks the retriever
  indexes, in the chunk's own vocabulary. Retrieval looks excellent because lexical overlap is high;
  real users do not phrase questions that way.
- **Prompt overfitting:** iterating the prompt against the full golden set is selection leakage with a
  text box instead of a hyperparameter grid.

### Detection checklist
Suspect leakage when a metric beats the published state of the art or human agreement on first try;
when one feature dominates importance; when random-split and time-split results diverge; when a
model trained on noise still scores above chance; and when production metrics fall far below offline
ones with no distribution shift to blame. Then audit provenance feature by feature: where was this
column computed, from what snapshot, at what time relative to the label?

## Example
The classic demonstration: 100 rows, 10,000 pure-noise features, labels unrelated to anything. Doing
feature selection on the full dataset before cross-validating produces impressive accuracy on data
that contains no signal at all, because the selector peeked at every fold's test labels. Putting the
selector inside the pipeline, so it is refitted on each fold's training rows, returns the metric to
chance where it belongs. The arithmetic of why: with 10,000 noise columns and 100 rows, a few dozen
columns correlate with the labels by luck alone, and the leaky selector picks exactly those, *using the
labels of the rows it will later be scored on*.

The second half shows row leakage. Each of 40 patients contributes ten visits that share a feature
fingerprint, and the label is a coin flip per patient, so nothing generalizes to a new patient. A
random row split almost always puts a sibling visit in training, and a 1-nearest-neighbour model scores
near-perfectly by looking it up. Splitting by patient exposes the truth.

```python
import numpy as np
from sklearn.feature_selection import SelectKBest, f_classif
from sklearn.linear_model import LogisticRegression
from sklearn.neighbors import KNeighborsClassifier
from sklearn.model_selection import StratifiedKFold, KFold, GroupKFold, cross_val_score
from sklearn.pipeline import make_pipeline

rng = np.random.default_rng(0)
X = rng.normal(size=(100, 10_000))                     # pure noise
y = rng.integers(0, 2, size=100)                       # labels independent of X
cv = StratifiedKFold(5, shuffle=True, random_state=0)
clf = LogisticRegression(max_iter=1000)

# WRONG: choose the 20 "best" features using all 100 rows, then cross-validate
X_sel = SelectKBest(f_classif, k=20).fit_transform(X, y)
leaky = cross_val_score(clf, X_sel, y, cv=cv).mean()

# RIGHT: selection is a pipeline step, refitted on each fold's training rows only
pipe = make_pipeline(SelectKBest(f_classif, k=20), LogisticRegression(max_iter=1000))
clean = cross_val_score(pipe, X, y, cv=cv).mean()
print(f"leaky CV accuracy: {leaky:.2f}   clean CV accuracy: {clean:.2f}")   # ~0.87 vs ~0.47

# Row leakage: 40 patients x 10 visits; each patient has a feature "fingerprint" and one
# random label, so the features carry no information about the label of an unseen patient.
groups = np.repeat(np.arange(40), 10)
fingerprint = rng.normal(size=(40, 8))
Xp = fingerprint[groups] + 0.3 * rng.normal(size=(400, 8))
yp = rng.integers(0, 2, size=40)[groups]
knn = KNeighborsClassifier(n_neighbors=1)              # a pure memorizer makes the leak obvious
by_row = cross_val_score(knn, Xp, yp, cv=KFold(5, shuffle=True, random_state=0)).mean()
by_patient = cross_val_score(knn, Xp, yp, cv=GroupKFold(5), groups=groups).mean()
print(f"random-row CV: {by_row:.2f}   patient-grouped CV: {by_patient:.2f}")
# Expect ~0.98 by row (a sibling visit is always in training) and near 0.5 by patient,
# noisy because there are only 40 independent units, not 400.
```

## Trade-offs
- Group- and time-based splits give honest estimates but higher variance and fewer usable folds,
  which matters when the dataset is small and every held-out entity is expensive.
- Freezing a test set and touching it rarely protects the number but slows iteration; teams
  compensate with a larger validation split and accept a less precise final estimate.
- Strict point-in-time feature computation prevents temporal leakage but complicates the data
  pipeline, which is a large part of why feature stores exist in hybrid ML systems.
- Deduplicating near-identical rows across splits removes optimistic bias, but aggressive
  near-duplicate thresholds can also remove legitimate recurring patterns the model must learn.
- Checking eval items against pretraining data for contamination is informative, but n-gram overlap
  misses paraphrases and translations, so a clean result is weaker evidence than a dirty one.

## Pitfalls
- Fitting scalers, imputers, encoders or feature selection before the split; the symptom is
  cross-validation scores that are higher than the score on a truly fresh batch of data.
- Random row splits on data with repeated entities or a time axis; the symptom is a large drop when
  you rerun with `GroupKFold` or a time-ordered split.
- A time-ordered split with no gap when labels look ahead (30-day churn, 90-day default); the
  symptom is a score that drops when you insert a one-horizon gap, and the earliest validation rows
  scoring best because their outcomes overlap training labels.
- A single feature with implausibly high importance; the symptom is that removing it drops the metric
  to a mundane level, and its provenance turns out to be post-outcome.
- Tuning prompts, retrieval settings or thresholds against the same set you report; the symptom is
  an offline number that improves every sprint while user-reported quality does not.
- Building the RAG golden set by having the model generate questions from indexed chunks; the symptom
  is near-perfect retrieval recall offline and frequent retrieval misses on real queries.
- Few-shot examples or fine-tuning data that overlap the eval set; the symptom is the model
  reproducing gold answers verbatim, sometimes including their formatting quirks.

## When to use
This is not a technique you adopt but a discipline you apply to every evaluation. Before trusting any
metric, ask three questions: what is the unit of independence and did we split on it; which steps
have a `fit` and do they all live inside the fold; and how many times has this test set influenced a
decision. For LLM systems add: did any eval item appear in a prompt, a fine-tuning file or the
retrieval corpus, and who wrote the eval questions. Measure the gap between random and
group/time splits, keep a log of test-set evaluations, and dedupe across splits with both exact and
near-duplicate checks. In interviews, the strong answer to "your model has 0.99 AUC, what do you do"
is "look for the leak before celebrating", followed by a concrete audit plan.

## Role lens
- **Engineer:** Puts every fitted transform inside the cross-validated pipeline, splits by group or
  time, and deduplicates eval items against prompts and fine-tuning data before reporting a metric.
- **Architect:** Defines the data-partition policy (frozen test set, point-in-time feature rules,
  entity-level splits) and the lineage needed to prove an eval set never touched training.
- **FDE:** Audits the customer's "proven" model or golden set for post-outcome fields and overlap
  with the corpus, since inherited evaluations are where most inflated numbers come from.

## Check yourself
**Q:** A RAG assistant reports 96% answer correctness. The golden set was produced by prompting the
same model to generate question–answer pairs from the indexed chunks, and the prompt was then refined
over thirty runs against that set. What is wrong with the number, and how would you rebuild the
evaluation?
**A:** Two leaks compound. The questions were written by the system under test in the chunks'
vocabulary, so retrieval enjoys lexical overlap real users will not provide and the answers mirror
what the model already produces; that inflates both retrieval and generation scores. Then thirty
rounds of prompt iteration against the full set turned the test set into a validation set, so the
96% is a selection-biased estimate. Rebuild it with questions sourced from real user logs or written
by subject-matter experts in their own phrasing, with answers verified independently of the model;
split into a development set for prompt iteration and a frozen test set evaluated only at release
points, with each evaluation logged; dedupe test questions against few-shot examples and any
fine-tuning data; and report the test number alongside the number of times it has been consulted.

## Quiz
### Q: Why does fitting a StandardScaler on the full dataset before splitting count as leakage, even though the labels are never used?
- [ ] Because the scaler changes the label distribution across folds
- [x] Because the test rows' statistics shape the transform the model trains on, so the model has indirectly seen the test distribution
- [ ] Because StandardScaler is not deterministic across folds
- [ ] It does not count as leakage; only label-dependent steps can leak
> Any fitted step carries information from the rows it saw. For a scaler the bias is usually small,
> but the same mistake with feature selection or target encoding is severe, so the rule is uniform:
> every fitted transform is refitted inside each fold on training rows only.

### Q: A churn model scores 0.99 AUC in cross-validation and 0.70 in production. Its top feature is `days_since_last_login`, computed from a database snapshot taken after the churn label window closed. Which kind of leakage is this?
- [ ] Group leakage, because the same customers appear in several folds
- [ ] Preprocessing leakage, because the feature was scaled before the split
- [x] Target leakage, because the feature was captured after the outcome and partly encodes it
- [ ] Selection leakage, because the test set was reused during tuning
> Customers who churned stopped logging in, so a post-window snapshot of inactivity is a consequence
> of the label, not a predictor available at decision time. The production drop is the feature
> reverting to its honest, much weaker predictive value.

### Q: You must forecast next month's demand for each of 400 existing stores from three years of history. Which split gives an honest estimate?
- [ ] A shuffled random split stratified by store
- [x] A time-ordered split where the validation window comes strictly after the training window
- [ ] GroupKFold holding out whole stores
- [ ] Leave-one-row-out cross-validation
> The deployment question is "given the past, predict the future for these stores", so the
> validation must be the future. A shuffled split lets the model train on months after the ones it is
> scored on. Holding out whole stores answers a different question: generalizing to new stores.
