## TL;DR
Dataset contamination is the presence of evaluation items, their paraphrases or solutions in a
model's training data, so a score measures memorization instead of capability. It is train/test
leakage at LLM scale, made unavoidable by training on web crawls that contain the benchmarks used to
grade the result. It matters because the inflation is uneven across models and tasks, so contaminated
comparisons pick the wrong model, and because your own golden dataset is contaminated as easily
through few-shot prompts and fine-tuning data.

## Why it exists
In classical machine learning the train/test split was yours: you held out rows and nothing in
training could see them. Pretraining a language model inverts this. The corpus is a crawl of the
public internet, and the public internet contains benchmark repositories, papers with examples in
them, blog posts walking through solutions, forum threads quoting questions, translations and
paraphrases, and the outputs of other models that were themselves tuned on the benchmark. The model
vendor rarely knows exactly what the crawl contains, and you, the downstream user, never do.

The consequences are concrete. A model that memorized a benchmark's answers scores higher without
being more capable, and the inflation differs by model (depending on crawl date and filtering) and by
benchmark (depending on how widely it was copied), so a leaderboard becomes a partial ranking of who
saw what. Model-selection decisions made on such scores are wrong in ways that only appear on your
own data. The same mechanism bites inside a team: copy five golden items into a few-shot prompt, or
fine-tune on a dump that includes the eval set, and the offline score jumps while production does not.

Two naive defences fail. "The vendor decontaminated" usually means n-gram filtering against known
benchmarks, which catches verbatim copies and misses paraphrases, translations and solution write-ups.
"Use a newer benchmark" works for a few months, until the new benchmark is on GitHub and in the next
crawl. Contamination is a standing condition to measure and manage, not a bug to fix once.

## How it works
### Routes by which it happens
- **Direct:** the test items, with or without answers, are in the pretraining or fine-tuning corpus.
- **Indirect:** paraphrases, translations, worked solutions and discussions of the items are in the
  corpus; the model learns the answer without ever seeing the exact text.
- **Transitive:** training on synthetic data generated by another model that had seen the benchmark;
  the knowledge moves without any benchmark text moving.
- **Temporal:** a benchmark published after the model's training cutoff is clean for that model and
  dirty for its successor, so comparisons across model generations are not like for like.
- **Evaluation-time:** few-shot examples drawn from the test split, or a golden dataset that was also
  used for prompt tuning or fine-tuning. This is the route teams control and most often get wrong.

### Detecting it with corpus access
If you can see the training data (your own fine-tuning set, or an open pretraining corpus), the
standard check is n-gram overlap: for each eval item, test whether any word n-gram of moderate length
appears in the corpus. The GPT-3 report used 13-gram overlap to flag items and then reported scores on
the clean and dirty subsets separately, which is the useful output: not "is it contaminated" but "how
much does the score change when flagged items are removed". Overlap checks are cheap (hash the
n-grams into a set or a Bloom filter) and conservative *because* they only catch near-verbatim text.

### Detecting it without corpus access
Most of the time you have only the model, so detection is behavioural:

- **Completion probes.** Give the model the first part of an item and ask it to continue; if it
  reproduces the rest nearly verbatim, including distinctive wording, it has seen it. Comparing a
  guided prompt (naming the dataset and split) against a generic one sharpens the signal.
- **Likelihood gaps.** Memorized text tends to have lower perplexity than fresh paraphrases of the
  same content; a large gap between the original item and a rewritten equivalent is suspicious.
- **Fresh-equivalent sets.** Build new items matching the benchmark's distribution and difficulty
  (the GSM1k study did this for grade-school math) and compare; a model whose score drops markedly on
  the fresh set was leaning on memorization, while one that holds steady was not. Across model families
  the drops reported in that study ranged from negligible to substantial, which is the point: the
  inflation is uneven.
- **Perturbation sensitivity.** Shuffle multiple-choice options, rename variables, paraphrase the
  question; a capable model is barely affected, a memorizing model drops.
- **Canary strings.** Benchmark authors embed a unique random string in the published files; if the
  model can reproduce the canary, the files were in training. This is what BIG-bench style canaries are
  for, and the same trick protects your own golden set.
- **Temporal splits.** Evaluate only on items created after the model's training cutoff
  (live-updated coding and reasoning benchmarks work this way), accepting that the clean window closes
  with every new model release.

### Why it is not binary
Contamination is a matter of degree. An item seen once in a trillion tokens may leave no trace; one
seen in a hundred copies with worked solutions is memorized. Models can memorize answers without
questions (seeing "the answer is C" in a discussion), and partial contamination can shift an aggregate
score by a few points, which is enough to reorder a leaderboard whose gaps are a few points.

### Preventing it for your own evaluations
Keep the golden dataset out of every training set, few-shot prompt and synthetic-generation prompt.
Run an n-gram overlap check between any fine-tuning data and the eval set before training, and remove
or quarantine hits. Keep a private held-out split that is never published or shared with the vendor.
Add a canary string to any eval file that leaves your repository. Record provenance for every item so
that when a public document it was drawn from turns up in a crawl, you know which items to re-examine.
And when quoting a public benchmark, report whether the score came from a model whose cutoff precedes
the benchmark's publication.

## Example
A corpus-side overlap check: hash every 13-word shingle in the training documents, flag each eval item
whose shingles intersect the set, and report accuracy on the clean and flagged subsets separately.
The split-score comparison is the actionable output. Numbers in the comment are illustrative.

```python
import hashlib, re
from collections import defaultdict

N = 13
def shingles(text: str, n: int = N):
    toks = re.findall(r"\w+", text.lower())
    for i in range(max(0, len(toks) - n + 1)):
        yield hashlib.blake2b(" ".join(toks[i:i + n]).encode(), digest_size=8).digest()

def build_index(train_docs) -> set:
    seen = set()
    for doc in train_docs:                      # streams a corpus; swap the set for a Bloom filter at scale
        seen.update(shingles(doc))
    return seen

def flag_items(eval_items, index: set) -> dict[str, bool]:
    return {it["id"]: any(s in index for s in shingles(it["question"] + " " + it["answer"]))
            for it in eval_items}

def split_scores(eval_items, flagged: dict, correct: dict) -> dict:
    buckets = defaultdict(list)
    for it in eval_items:
        buckets["flagged" if flagged[it["id"]] else "clean"].append(correct[it["id"]])
    return {k: (len(v), round(sum(v) / len(v), 3)) for k, v in buckets.items() if v}

index = build_index(iter_training_docs())       # your fine-tuning set, or an open pretraining shard
flagged = flag_items(eval_items, index)
print(split_scores(eval_items, flagged, model_correct))
# e.g. {'clean': (712, 0.78), 'flagged': (288, 0.93)}  -> a 15-point gap on flagged items is a
# memorization signal; report the clean-subset score and remove flagged items from fine-tuning data.
```

A short n-gram (5 or 8 words) over-flags common phrasing; a long one (20+) misses light edits. Thirteen
is a conventional compromise, not a law, and the check only ever catches near-verbatim overlap, so a
clean result is "not detectably contaminated", not "clean".

## Trade-offs
- N-gram overlap is cheap, scalable and precise about verbatim copies, but it misses paraphrases and
  translations entirely, so a clean result under it is weak evidence.
- Fresh-equivalent sets give the most convincing behavioural evidence, but writing new items that match
  the original difficulty distribution is expensive and the fresh set itself becomes stale once shared.
- Private held-out sets are immune to crawl contamination, but they cannot be independently
  reproduced, so results on them carry less public credibility.
- Aggressive decontamination of training data protects the eval, but removing every document that
  overlaps a benchmark also removes legitimate educational content and can reduce model quality.

## Pitfalls
- Trusting a leaderboard without checking cutoffs; the symptom is a model that leads on a 2021
  benchmark and underperforms a cheaper, newer model on private tasks of the same kind.
- Few-shot examples drawn from the eval split; the symptom is an offline jump of several points on the
  day the prompt changed, with no movement in production metrics.
- Fine-tuning on a data dump that includes golden items; the symptom is near-perfect eval scores on the
  tuned model and a steep drop on a freshly labeled batch.
- Treating an n-gram-clean benchmark as uncontaminated; the symptom is a model that reproduces the
  benchmark's answers for paraphrased questions while passing the overlap check.
- Using a model to generate "new" eval items from public documents; the symptom is items the model
  already answers from memory because the source documents were in its crawl.
- Publishing the golden set in a public repository for convenience; the symptom is that next year's
  model aces it and the team cannot tell improvement from memorization.

## When to use
Think about contamination every time a benchmark score is used to make a decision, and every time an
eval set or fine-tuning set changes hands. Before trusting a public score, check whether the model's
training cutoff precedes the benchmark and whether the reporter separated clean and flagged subsets.
Before fine-tuning, run an overlap check between training data and every eval set you care about.
Before sharing an eval set, add a canary and keep a private held-out split. In day-to-day work the
check is a short script in the data pipeline and a line in the model-selection memo; in interviews,
expect to be asked how you would tell whether a model memorized a benchmark when you cannot see its
training data, and the strong answer names at least two behavioural probes.

## Role lens
- **Engineer:** Adds an overlap check between fine-tuning data and eval sets to the training pipeline,
  and keeps golden items out of few-shot prompts and generation scripts.
- **Architect:** Sets the policy for private held-out sets, canaries and provenance tracking, and
  requires clean-subset reporting when benchmark scores feed a model decision.
- **FDE:** Explains to a customer why a model's public benchmark lead may not transfer, and runs a
  fresh, customer-specific eval whose items the model cannot have seen.

## Check yourself
**Q:** You suspect a model's strong score on a public math benchmark is due to contamination, but you
have no access to its training data. Describe two independent ways to test the suspicion and what
result would confirm it.
**A:** First, a completion probe: feed the first half of benchmark problems and ask the model to
continue; near-verbatim reproduction of the remaining text, including idiosyncratic wording and
numbers, indicates the items were in training, and comparing a prompt that names the dataset against a
generic one strengthens the signal. Second, a fresh-equivalent set: write or commission new problems
matched in topic, difficulty and format, evaluate both sets under the same protocol, and compare; a
drop of several points on the fresh set, beyond the confidence interval of the set size, indicates the
original score leaned on memorization. A cheaper third check is perturbation: paraphrase questions or
change numeric values and watch whether accuracy collapses. Convergent evidence from two of these is
what I would act on.

## Quiz
### Q: Why does an n-gram overlap check between training data and a benchmark give only weak evidence that the benchmark is clean?
- [ ] N-gram checks are too slow to run on full corpora
- [x] It only detects near-verbatim copies, so paraphrases, translations and solution write-ups pass unnoticed
- [ ] Models cannot memorize text shorter than the n-gram length
- [ ] Benchmarks are rarely copied verbatim onto the web
> Overlap matching is exact on token sequences. Indirect contamination through rewritten or discussed
> items leaves no matching 13-gram, yet still teaches the model the answers, so a clean overlap result
> rules out only one route.

### Q: A team fine-tunes a model on a customer data dump and the golden-set pass rate jumps from 71% to 98%. What should they check first?
- [ ] Whether the learning rate was too high
- [x] Whether the dump contained the golden items, by running an overlap check between the two
- [ ] Whether the eval harness cached old outputs
- [ ] Whether the judge model was changed
> A jump of that size is the classic symptom of evaluation-time contamination. Checking overlap between
> training data and the eval set is cheap and should precede any celebration or any other diagnosis.

### Q: What does a canary string in a published eval file allow you to do later?
- [ ] Decrypt the answers if the file is leaked
- [ ] Detect which users downloaded the file
- [x] Test whether a model saw the file in training by asking it to reproduce the string
- [ ] Prevent the file from being indexed by web crawlers
> A unique random string has no reason to appear in a model's output unless the file containing it was
> in the training data. It does not stop crawling or leaking; it makes the leak detectable after the
> fact.
