## TL;DR
Declare what you *need* as ranges, record what you *got* as exact versions with hashes, and install only
from the record. A lockfile turns "the set of packages that satisfied my constraints on the day I
resolved" into a committed artifact, so every developer, CI run and container installs the same bytes. For
applications this is non-negotiable; libraries publish ranges and leave locking to whoever deploys them.

## Why it exists
A typical AI service declares perhaps fifteen direct dependencies and installs well over a hundred. Each
direct dependency allows a range of versions of its own dependencies, and new releases appear daily. With
only ranges, `pip install` on Tuesday and on Friday can produce different environments from the same
source tree. The failure is rarely loud at install time; it appears later as a changed default, a removed
keyword argument or a new validation rule, in a package nobody on the team chose directly.

The naive responses both fail. Pinning nothing ("always get the latest fixes") means every build is a new,
untested combination, so a green CI run on Monday says nothing about Friday's deploy. Pinning everything by
hand in `requirements.txt` freezes direct dependencies but misses transitive ones unless you freeze the whole
environment, and then upgrades become painful manual surgery, so teams stop upgrading and accumulate
vulnerable versions. A lockfile, generated by a resolver from declared intent, gives you exactness *and*
cheap, reviewable upgrades.

## How it works
### Two layers: constraints and resolution
In `pyproject.toml` you declare intent with PEP 440 specifiers: `openai>=1.40,<2`, `httpx>=0.27`. A resolver
(uv, Poetry, pip-compile) searches for one version of every package in the transitive graph that satisfies
all constraints at once, then writes the result. Keeping the two layers separate is the point: humans reason
about compatibility in ranges; machines record the exact solution.

### What a lockfile records
- **Exact versions** for every package, direct and transitive.
- **Hashes** of the distribution files. With hash checking (`pip install --require-hashes`, or tools that
  verify lock hashes automatically), an install fails if a file's bytes differ from what was locked,
  *because* a version number alone does not prove you got the same artifact: a compromised mirror or index
  could serve different bytes under the same name.
- **Markers and platforms.** Some packages differ by OS, CPU architecture or Python version. A
  *universal* lock (uv.lock, poetry.lock) records resolutions for all supported environments; a
  platform-specific one (a pip-compile output run on Linux) is only valid where it was resolved.
- **Sources.** Which index each package came from, which matters for torch CUDA wheels and private mirrors.

PEP 751 defines a standard `pylock.toml` format so that different tools can produce and consume the same
lockfile; tool-specific formats remain common.

### Applications vs libraries
An application is the end of the dependency chain, so it should lock exactly. A library is installed
alongside other people's dependencies; if it pinned `httpx==0.27.2`, any application also needing a newer
httpx could not install both. Libraries therefore declare the widest range they are actually tested with.
Upper bounds (`<2`) on libraries are debated: they prevent breakage from a future major version but cause
unsatisfiable resolutions when that version ships and the library is not updated. Lower bounds should reflect
the oldest version you actually test.

### Upgrading on purpose
Pinning is safe only if upgrades keep happening. Bots (Dependabot, Renovate) or a scheduled job run
`uv lock --upgrade` (or `--upgrade-package openai` for one package), open a pull request with the lock diff,
and let CI and the eval suite decide. Small, frequent upgrades are cheaper to debug than a year of drift
landing at once, and they keep security fixes flowing.

### What a lock does not pin
The interpreter version, OS libraries (glibc, CUDA drivers), the base container image and model weights are
outside the Python lock. Reproducibility needs those pinned too: a `requires-python` range plus a
`.python-version`, an image digest, and model revisions or checksums.

## Example
A worked failure and its fix. A RAG service declares `openai>=1.0` and `httpx` with no lockfile. The image is
rebuilt for an unrelated config change; the resolver picks up a new minor release of the HTTP client in which
a long-deprecated constructor argument was removed. The SDK version that was also resolved still passes that
argument, so every request fails at client construction with a `TypeError` about an unexpected keyword. Code,
prompts and tests are unchanged; only the environment moved. (A real instance of this pattern hit older
OpenAI Python SDK releases when httpx 0.28 removed its `proxies` argument.)

With a lockfile the sequence is different. The rebuild installs exactly the locked versions, so production is
unaffected. Separately, the weekly upgrade job runs `uv lock --upgrade` and opens a pull request whose diff shows
the HTTP client moving one minor version. CI runs the unit tests and a small integration test that constructs
the real SDK client, which fails with the same `TypeError`, so the upgrade is held back. The fix is to also
upgrade the SDK to a release that supports the new client, or to add a temporary upper bound (`httpx<0.28`)
with a comment and a ticket to remove it. The failure happened in a pull request instead of in production,
and the cause was visible as a two-line lock diff rather than reconstructed from logs.

## Trade-offs
- Exact locks make builds reproducible and incidents bisectable, but you stop receiving fixes automatically;
  that is only safe when an automated upgrade process actually runs and its PRs get merged.
- Hash checking defends against tampered or substituted artifacts, but breaks when a package must be built
  from source differently per platform or when an internal mirror re-packages files; in those cases verify at
  the mirror instead.
- A universal lock serves every developer OS and CI image from one file, but may fail to resolve packages
  that only exist for some platforms; a Linux-only lock is simpler when deployment is the only target.
- Tight upper bounds in a library protect users from untested majors, but cause unresolvable conflicts in
  applications; for libraries, testing against new releases quickly usually beats capping.

## Pitfalls
- Not committing the lockfile, or adding it to `.gitignore`; the symptom is "works locally, fails in CI"
  with different transitive versions in each environment.
- Installing with `pip install .` in Docker while the lock sits unused in the repo; the symptom is images that
  contain versions which appear nowhere in the lockfile.
- Pinning exact versions in a published library's dependencies; the symptom is user bug reports saying your
  package cannot be installed alongside another common package.
- Locking but never upgrading; the symptom is a security scan listing many known vulnerabilities whose fixes
  shipped months ago, and an eventual upgrade that changes dozens of packages at once.
- Treating the Python lock as full reproducibility; the symptom is identical locks giving different results
  because the base image, CUDA runtime or model revision changed underneath.

## When to use
Lock every application, service, notebook environment that feeds production, and evaluation harness, because
eval results are only comparable when the environment is fixed. Do not lock a library's published
dependencies; lock its development environment for CI instead. Install with a check that the lock matches
the declared dependencies (`uv sync --locked`, `poetry install` with a check that the lock is current) and
with hash verification where your tooling allows. Measure lock age and the number of packages behind
latest, and schedule upgrades. In interviews, the expected answer separates application from library policy
and explains what hashes protect against.

## Role lens
- **Engineer:** Commits the lock, reads lock diffs in upgrade PRs, and adds a narrowly scoped temporary bound
  with a ticket when an upstream release breaks something.
- **Architect:** Defines organization-wide policy: locking for deployables, upgrade cadence, hash
  verification, approved indexes, and how base images and model revisions are pinned alongside.
- **FDE:** Reproduces the customer's exact environment from their lock or image when debugging, and ships
  locked, mirror-compatible requirements that pass their artifact review.

## Check yourself
**Q:** You maintain both an internal Python library used by several services and one of those services.
How should version constraints differ between them, and what goes wrong if you use the service's policy for
the library?
**A:** The service is a leaf: it locks every package exactly, with hashes, and installs only from the lock,
because reproducibility of what runs matters most. The library is installed alongside other services'
dependencies, so it declares ranges covering versions it is tested against, perhaps with conservative bounds,
and locks only its own CI environment. If the library pinned exact versions, every consuming service would
be forced onto those versions, and any service needing a different version of a shared package (an SDK,
pydantic, httpx) would hit an unresolvable conflict.

## Quiz
### Q: What does hash checking in a lockfile protect against that exact version pins alone do not?
- [ ] A dependency releasing a new minor version
- [x] Receiving different file contents under the same package name and version
- [ ] Resolution conflicts between transitive dependencies
- [ ] Packages that require a newer Python version
> A version number names a release; a hash identifies the exact bytes. If an index or mirror serves a
> tampered or substituted file, the hash no longer matches and installation fails instead of proceeding.

### Q: Why should a widely used library avoid exact pins in its declared dependencies?
- [ ] Exact pins slow down import time
- [ ] PyPI rejects packages with exact pins
- [ ] Exact pins disable hash checking for users
- [x] Applications installing it with other packages may be unable to find a version set that satisfies everyone
> Every package in an environment must agree on one version of each dependency. A library's exact pins
> become everyone's constraints, causing unresolvable conflicts; applications are the right place to lock.

### Q: Two builds from the same commit and the same lockfile give different model outputs. Which is a plausible cause?
- [ ] The lockfile hashes were ignored, so packages differed
- [x] Something outside the Python lock changed, such as the base image, CUDA runtime or model revision
- [ ] Lockfiles do not pin transitive dependencies
- [ ] The resolver re-ran and chose different versions
> A lock pins Python packages, including transitive ones, but not the interpreter build, system libraries,
> drivers or model weights. Those need their own pins, such as image digests and model revisions.
