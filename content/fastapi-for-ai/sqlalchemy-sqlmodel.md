## TL;DR
SQLAlchemy is Python's standard SQL toolkit: Core builds and executes SQL expressions safely, the ORM
maps classes to tables and tracks changes in a unit of work. SQLModel wraps SQLAlchemy's declarative
models in Pydantic so one class can be both a table and an API schema, which is why FastAPI projects
reach for it. Use SQLModel when the storage and API shapes agree; drop to plain SQLAlchemy 2.0 when
you need its full feature set or when the two shapes diverge, which they eventually do.

## Why it exists
AI backends carry a lot of relational state: conversations and messages with JSON tool-call payloads,
jobs and their progress, documents and chunks with embeddings, evaluation runs and scores. Writing SQL
strings by hand gets three things wrong at once. Interpolated values invite injection; a column list
repeated in a Pydantic model, an INSERT and a SELECT drifts out of sync; and loading related rows
(every message of every conversation) is coded as a loop of queries that nobody notices until the
table is large.

SQLAlchemy's Core answers the first two with an expression language that compiles to parameterised SQL
for whichever dialect you run, and the ORM answers the third with relationships, loading strategies
and a unit of work that orders INSERTs and UPDATEs by foreign-key dependency. Its declarative models
also become the input to Alembic, so schema changes are generated from code rather than typed twice.

SQLModel exists because FastAPI already forces a Pydantic model for every request and response, and
duplicating those fields in a SQLAlchemy model is tedious and error-prone. By making a class
simultaneously a Pydantic model and a SQLAlchemy declarative model, SQLModel collapses the duplication
and keeps validation, OpenAPI docs and the table definition in one place. The naive alternative, plain
Pydantic plus raw asyncpg, works and is fast, but you give up autogenerated migrations, relationship
loading and the identity map, and you end up rebuilding a worse ORM by hand.

## How it works
### Core versus ORM
Core is `Table`, `select()`, `insert()`, `update()` and an `Engine` whose connections execute compiled
statements with bound parameters. The ORM sits on top: a `DeclarativeBase` subclass with
`id: Mapped[int] = mapped_column(primary_key=True)` style attributes, and a `Session` that holds an
identity map (one Python object per row per session) and a unit of work. `session.add()` registers an
object, `flush()` emits SQL in dependency order, `commit()` flushes, commits and by default *expires*
every loaded instance so the next attribute access reloads from the database. Two consequences of the
unit of work surprise people. Autoflush: before a query runs, pending changes are flushed so the query
sees them, which means a `select()` can raise an `IntegrityError` that really belongs to an earlier
`add()`. And the identity map means one session holds one object per primary key: `session.get()` for a
row already loaded skips the database entirely, and even a fresh `select()` that does hit the database
hands back the existing object without overwriting its loaded attributes (unless you ask for
`populate_existing`), so a long-lived session serves stale data while a short per-request session
does not. That expiry default,
`expire_on_commit=True`, is the trap in async code: the reload is implicit IO and raises
`MissingGreenlet`, so async sessions are created with `expire_on_commit=False`.

The 2.0 query style is `session.execute(select(Message).where(...))`, which returns rows, or
`session.scalars(...)`, which returns objects; the legacy `session.query()` still works but is not
where new features land. Relationship loading is lazy by default, which is the N+1 problem waiting to
happen; `selectinload()` issues one extra `IN (...)` query per relationship, `joinedload()` folds it into
a JOIN, and `raiseload()` turns accidental lazy loads into errors during tests. JSON columns store tool
calls and metadata; the `pgvector` package adds a `Vector(dim)` column type for embeddings.

### What SQLModel adds
`class Message(SQLModel, table=True)` declares fields with ordinary type annotations; each field is a
Pydantic field *and* a column. `Field(primary_key=True, index=True, foreign_key="conversation.id")`
covers the common column options, `Field(sa_column=Column(JSON))` hands over a full SQLAlchemy column
for anything else (it cannot be combined with `primary_key`, `index` or `foreign_key`, which then go
on the `Column` itself), and `Relationship(back_populates=...)` maps relationships. A `SQLModel` subclass *without* `table=True` is a pure Pydantic schema, so the
idiom is a shared base with the common fields, a table model that adds `id` and timestamps, and
`Create`/`Read` schemas that add or omit fields for the API. `sqlmodel.Session` and the async session
in `sqlmodel.ext.asyncio.session` are SQLAlchemy sessions with a `session.exec(select(...))` method
that returns typed scalars directly. Two sharp edges are documented: table models do not run Pydantic
validation when instantiated, so validate incoming data through a non-table schema and convert with
`Message.model_validate(payload, update={...})`; and SQLModel tracks SQLAlchemy with some lag, so a
feature missing from SQLModel's surface is usually reachable through `sa_column` or `sa_relationship`
rather than absent. Because its metadata *is* SQLAlchemy metadata, Alembic works unchanged.

### Choosing between them
SQLModel pays off when the API payload and the row look alike and the project is small enough that one
set of classes is a feature. Plain SQLAlchemy 2.0 pays off when storage and API shapes differ
(denormalised read models, columns the client must never see), when you use advanced mapping (hybrid
properties, polymorphism, composite types), or when the team already knows it. For hot paths such as
bulk-inserting a million chunks, drop to Core `insert()` with a list of dicts or to the driver's bulk
copy, inside the same engine.

## Example
A SQLModel schema for conversations and messages with the table/schema split, and two sync endpoints.
Sync endpoints run on the thread pool, which is fine for CRUD; the async session is a drop-in for the
pattern in the async database lesson.

```python
from datetime import datetime, timezone
from typing import Optional
from fastapi import Depends, FastAPI
from sqlalchemy import JSON, Column
from sqlmodel import Field, Relationship, Session, SQLModel, create_engine, select

class Conversation(SQLModel, table=True):
    id: Optional[int] = Field(default=None, primary_key=True)
    user_id: str = Field(index=True)
    messages: list["Message"] = Relationship(back_populates="conversation")

class MessageBase(SQLModel):                        # fields the API and the table agree on
    role: str
    content: str
    tool_calls: Optional[dict] = Field(default=None, sa_column=Column(JSON))

class Message(MessageBase, table=True):
    id: Optional[int] = Field(default=None, primary_key=True)
    conversation_id: int = Field(foreign_key="conversation.id", index=True)
    created_at: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))
    conversation: Conversation = Relationship(back_populates="messages")

class MessageCreate(MessageBase): pass               # clients may not set id or timestamps
class MessageRead(MessageBase):
    id: int
    created_at: datetime

engine = create_engine("postgresql+psycopg://app:pw@db/app", pool_pre_ping=True)
app = FastAPI()

def get_session():
    with Session(engine) as session:
        yield session

@app.post("/conversations/{conv_id}/messages", response_model=MessageRead)
def add_message(conv_id: int, body: MessageCreate, session: Session = Depends(get_session)):
    msg = Message.model_validate(body, update={"conversation_id": conv_id})   # validated via the schema
    session.add(msg); session.commit(); session.refresh(msg)
    return msg

@app.get("/conversations/{conv_id}/messages", response_model=list[MessageRead])
def list_messages(conv_id: int, session: Session = Depends(get_session)):
    stmt = select(Message).where(Message.conversation_id == conv_id).order_by(Message.id)
    return session.exec(stmt).all()
```

## Trade-offs
- The ORM's identity map and unit of work remove whole classes of bugs, but they add per-object
  overhead; once ingestion reaches thousands of chunks per batch, Core `insert()` with a list of dicts
  (or the 2.0 ORM bulk form `session.execute(insert(Chunk), rows)`) and driver-level `COPY` are
  typically several times faster than adding objects one by one; measure on your own data.
- SQLModel's single class per entity removes duplication, but couples the API contract to the table;
  the moment a client must not see a column or a response needs a computed shape, you are back to
  separate schemas and have lost the benefit.
- Lazy loading makes simple code simple, but each relationship access is a query; explicit
  `selectinload` is more typing and is the only way the query count stays flat as data grows.
- Typed 2.0-style models give IDE and type-checker support, but mixing them with legacy `Query` code
  (still supported, labelled legacy rather than deprecated) leaves two query idioms with different
  return shapes and weaker typing on the legacy half; migrate module by module.

## Pitfalls
- `expire_on_commit` left at its default in async sessions; the symptom is `MissingGreenlet` on the
  first attribute read after `commit()`.
- Lazy relationship access inside a loop; the symptom is one query plus one per row in the SQL log,
  and a list endpoint whose latency grows linearly with conversation length.
- Using the table model as the request body; the symptom is clients setting `id` or `created_at`, and
  inputs that bypass validation because table models skip it.
- A module-level session shared across requests; the symptom is cross-request data leaks and
  "Session is already flushing" or stale-object errors under concurrency.
- Mutating a JSON column in place (`msg.tool_calls["x"] = 1`); the symptom is a commit that writes
  nothing, because SQLAlchemy only detects reassignment unless the column uses a mutable wrapper.
- Foreign-key columns without an index; the symptom is a sequential scan on every "messages for
  conversation" query, since Postgres does not index foreign keys automatically.

## When to use
Reach for SQLAlchemy whenever a FastAPI service owns relational data, which is most of them; choose
SQLModel for small to medium services whose API and storage shapes align and whose team wants one set
of models, and plain SQLAlchemy 2.0 when the domain or the mapping gets complex. Measure query counts
per request (the N+1 detector), time in session, and bulk-insert throughput. In day-to-day work the
recurring tasks are defining the Create/Read/table split, choosing loading strategies, and keeping
models and migrations in step. In interviews, be ready to explain identity map and unit of work,
why `expire_on_commit` matters in async code, and what SQLModel actually is underneath.

## Role lens
- **Engineer:** Defines models and schemas, picks loading strategies per endpoint, and knows when to
  drop to Core or the driver for bulk writes of chunks and embeddings.
- **Architect:** Decides SQLModel versus plain SQLAlchemy for the codebase, sets the rule that API
  schemas and table models are separate classes, and owns the data model that migrations evolve.
- **FDE:** Reads a customer's existing SQLAlchemy models to wire an AI feature into their schema
  without breaking their migrations or their ORM conventions.

## Check yourself
**Q:** A list endpoint returning conversations with their messages is fast in development and takes
seconds in production. What is happening and how do you fix it without changing the response?
**A:** Almost certainly N+1 loading: the query fetches the conversations, and then the response
serialiser touches `conversation.messages` for each one, which lazily issues one query per
conversation. In development there are five conversations; in production there are five hundred, so
the endpoint runs five hundred and one queries. Confirm by logging SQL or counting statements in a
test. Fix it by adding `options(selectinload(Conversation.messages))` to the select, which loads all
messages in one extra `IN` query, or `joinedload` if the result set is small. In async code eager
loading is also effectively required, because the implicit lazy load raises `MissingGreenlet` (the
explicit `await conv.awaitable_attrs.messages` from `AsyncAttrs` avoids the error but is still one
query per conversation). Add `raiseload` in tests so the regression cannot return.

## Quiz
### Q: What is the one thing SQLModel adds on top of SQLAlchemy?
- [ ] A faster asynchronous driver for PostgreSQL
- [x] Classes that are simultaneously Pydantic models and SQLAlchemy declarative models, so one definition serves validation, docs and the table
- [ ] Automatic schema migrations without Alembic
- [ ] A query cache shared across requests
> SQLModel is a thin layer that merges the two class systems. Its sessions, engine, metadata and
> migrations are all SQLAlchemy's; what it buys is the removal of duplicated field definitions.

### Q: Why define a separate MessageCreate schema instead of accepting the Message table model as the request body?
- [ ] FastAPI cannot generate OpenAPI docs from table models
- [ ] Table models cannot be used with `response_model`
- [x] Clients could set server-owned fields such as id and timestamps, and table models skip Pydantic validation on instantiation
- [ ] Table models are not JSON-serialisable
> The non-table schema is where validation happens and where the client-facing contract lives. The
> table model is converted from it with `model_validate(..., update=...)` once the server adds its fields.

### Q: In an async session with the default expire_on_commit, what happens when you read an attribute after commit()?
- [ ] The cached value from before the commit is returned
- [ ] The attribute is None until refresh() is called
- [x] The ORM tries to reload the row synchronously and raises MissingGreenlet
- [ ] The read is converted into an awaitable automatically
> Commit expires loaded instances so the next access reloads. That reload is implicit IO the async
> bridge cannot perform, which is why async sessions set `expire_on_commit=False` or call `refresh()`.
